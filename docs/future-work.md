# 后续事项

本文记录设计访谈中明确延后的事项，以及只有出现测量证据后才考虑的升级。它不是 `0.1.0` 的承诺清单；未满足触发条件时遵循 YAGNI，不提前实现。

## 明确延后的玩法事项

- **更智能的决策**：首版只要求尸潮推进、原版近距离索敌和受阻挖掘。以后再决定是否加入目标共享、失去视野后的追踪记忆、声音吸引、包围/侧翼、路线预测或危险规避。
- **睡觉的对抗玩法**：首版允许按原版规则睡过夜。以后若玩家能轻易绕过核心玩法，再讨论禁止睡眠、睡后继续尸潮或其他补偿机制。
- **尸潮死亡奖励和平衡**：首版尸潮成员不掉物品或经验。以后根据战斗成本、刷怪场滥用和掉落实体性能数据决定奖励方式；不要直接恢复无限原版掉落。
- **多个生成方向**：首版每个玩家群组每晚只有一股尸潮。以后需要包围感时再扩展为多个方向，并重新评估路线数量和生成性能。
- **更多僵尸类型**：首版不接管 `Husk`、`Drowned` 或 `Zombie Villager`。扩展前需分别明确沙漠、水下、村民转化、数量预算、白天清理和专属行为。
- **其他维度**：首版仅主世界生效。支持下界或末地前需重新定义昼夜、生成位置、目标生物和清理规则。
- **额外内容资产**：新方块、物品、模型、GUI 和声音不属于首版。只有核心尸潮体验验证后，再按具体玩法需求逐项决定。

## 由性能数据触发的技术事项

- **多高度流场与异步 Worker**：只有 JFR 证明主线程错峰寻路和共享路线仍是主要瓶颈时再实现。必须使用主线程生成的不可变地形快照，Worker 不得访问或修改活的世界、区块或实体。
- **尸潮区块票据上限**：若任一 Fabric/NeoForge 固定基准不达标，暂停 `0.1.0` 发布并重新讨论全服票据硬上限、外圈冻结或更粗的远距离仿真。
- **专用碰撞 broadphase**：只有 Profiler 证明实体候选扫描而非真实接触对是主要瓶颈时再考虑。不要缩小原版 AABB；密集接触的最坏成本仍需邻居上限兜底。
- **自定义网络同步 LOD**：只有网络和客户端帧时间分析证明原版实体位置包是瓶颈时再做。首版只降低远处动画、阴影和非必要视觉效果。
- **距离与频率校准**：近中远距离阈值、重新寻路频率、碰撞邻居上限、共享路线 TTL、卡死阈值和挖掘名额都要以固定基准校准。只有不同硬件确实需要管理员控制时，才把内部参数提升为稳定配置接口。
- **方块掉落实体控制**：首版使用原版掉落合并和寿命。只有围墙/山体基准证明 FakePlayer 挖掘产生的掉落实体成为瓶颈时，再讨论缩短寿命、数量预算或其他清理规则。

## 由实际故障触发的兼容事项

- **平台功能降级**：FakePlayer、区块票据、SavedData 或平台事件失败时如何降级，按遇到的具体故障决定；不提前建设通用恢复框架。
- **领地与权限模组**：首版只保证标准破坏事件。遇到只识别真人玩家、拒绝 FakePlayer 或使用私有权限接口的模组时，再决定专用适配或明确不兼容。
- **自然生成事件兼容**：接管普通 Zombie 自然种群后，依赖原版自然生成事件的模组可能失效；收到具体兼容报告后再处理。
- **原版 Zombie AI 冲突**：其他模组若替换或深度修改原版 Zombie AI，可能与尸潮行为注入冲突；按具体 Mixin/事件冲突建立兼容方案。
- **未知方块实体**：完整 FakePlayer 破坏仍可能被模组拒绝或产生特殊掉落。只有出现复制、吞物或权限绕过案例时才添加黑名单或专用适配。
- **卸载迁移**：首版不提供专用迁移器。只有残留尸潮标记或 SavedData 在实际卸载场景中造成问题时再增加清理工具。
- **Minecraft 版本升级**：升级游戏版本时重新核对 Mixin 锚点、PathFinder、区块票据、FakePlayer 和两端平台 API，不假设 `1.21.1` 的实现细节仍成立。
